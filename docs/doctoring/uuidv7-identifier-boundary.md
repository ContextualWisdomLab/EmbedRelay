# UUIDv7 identifier boundary

## Decision

EmbedRelay uses opaque UUID version 7 identifiers for durable registry and audit identities. The Rust contract accepts only UUIDs using the RFC 9562 variant and version-7 layout and generates new identifiers with the `uuid` crate's process-local monotonic UUIDv7 generator.

This slice deliberately does **not** assign authorization, tenant, routing, or business meaning to the timestamp bits. An identifier proves only that its syntax is an accepted EmbedRelay identifier; every tenant and access-control decision remains a separate authenticated policy decision.

## Why UUIDv7

RFC 9562 places the Unix epoch timestamp in milliseconds in the most significant 48 bits of UUIDv7 and reserves the remaining non-version/non-variant bits for random data or monotonic extensions. That layout provides time-sortable opaque keys without embedding a node identifier. It is appropriate for later PostgreSQL registry and append-only audit indexes where insertion locality matters, while keeping identity independent from customer-controlled names.

The implementation rejects syntactically valid UUIDs when either the variant is outside the RFC 9562 layout or the version is not 7. The public parse error is intentionally non-reflecting: malformed caller input is never copied into the error text.

## Ordering boundary

`uuid::Uuid::now_v7()` guarantees creation ordering for UUIDv7 values produced by the same process. EmbedRelay does not claim a stronger global ordering guarantee across processes, hosts, or clock resets. Business chronology and audit ordering must therefore retain explicit event timestamps and transaction ordering rather than infer them solely from UUID bytes.

## Security and privacy boundary

- Treat every identifier as public opaque metadata unless the surrounding resource is independently authorized.
- Never derive tenant membership, permissions, retention, or provenance from UUID timestamp bits.
- Never place customer names, model identifiers, secrets, or host identifiers into the random portion.
- Parse external identifiers through `RelayIdentifier`; do not accept generic UUID versions at persistence boundaries.
- Preserve database tenant isolation and row-level security independently of identifier uniqueness.

## Rollback

No database schema or persisted production data is introduced by this slice. Before the later PostgreSQL migration is released, rollback is a code-only revert of the identifier module, tests, export, doctoring, and changelog entry. Once UUIDv7 values become persisted external identifiers, rollback must preserve those values and their parser compatibility; changing identifier format would require an explicit forward migration rather than in-place reinterpretation.

## Acceptance criteria

1. The RFC 9562 Appendix A.6 UUIDv7 test vector parses and canonicalizes.
2. Generated values use UUID version 7 and the RFC 9562 variant.
3. Successive values generated by one process preserve creation ordering.
4. Malformed UUID text, non-v7 UUIDs, and non-RFC variants fail closed with stable non-reflecting errors.
5. The production identifier module retains exact 100% line, region, function, and branch coverage under the repository LLVM coverage gate.
6. No authorization or tenant decision depends on UUID timestamp material.
